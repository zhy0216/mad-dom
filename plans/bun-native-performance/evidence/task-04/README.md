# Task 04 checksum IO evidence

Production change: `verify()` snapshots directory membership once into a Set,
then preserves manifest Map insertion order and sequential read/hash/error behavior.
Generate, manifest read/write strategy, independent Bun capability fallbacks and
all release/package/platform contracts retain the existing implementation.

The actual checksum CLI is now exercised by six additional rows in
`scripts/bench-bun-io.mjs`: small/many/large × generate/verify. The existing schema
and five IO/facade rows remain. Every internal invocation and direct CLI process
validates the full manifest and every fixture file, with complete raw timings,
stdout/stderr/exits, expected digests, filenames and absolute commands retained.

Formal **generate overwrites an existing valid manifest**: fixture preparation
creates it, and all timed rounds use the same state on both sides. Checking that
pre-existing correct content alone cannot prove that a generator actually wrote.
The separate untimed [write proof](write-proof.mjs) deletes or poisons the manifest
before running the actual reference/candidate CLI, on both runtimes and both IO
modes, then checks the complete generated bytes, sorted digests and every tarball.
It also runs a temporary no-op generator that prints the exact success text with
exit 0; the same oracle must reject it. [All 32 probe records](write-proof.json)
include the actual commands, outputs, fixture contents and source/runtime/image
fingerprints. The probe writes only temporary fixtures, never reference source.
All 16 actual-CLI cases passed; all 16 success-printing no-op cases were rejected.
Both final host IO test runs passed 44 tests / 513 assertions, with no failures or
skips. The complete supplemental driver exited 0 under the existing build-test gate.
The permanent regression test is `checksum generate replaces poisoned manifests
and rejects a no-op generator` in
[bun-host-io.test.js](../../../../tests/bun/bun-host-io.test.js).
Generate production source is unchanged; this independent proof supplements the
original samples without changing their overwrite window or rerunning campaigns.

All installation/build/test/selftest commands are logged in `commands/` with the
complete gate command, environment, start/end, exit and output. `verify.mjs` also
records every nested check and its complete output. `remaining-sampling.json`
records all paired sampling and audit commands nested under one exclusive gate.
The coordinator's activity records are copied into final `activity.jsonl`.
No benchmark worker detaches; all subprocesses are awaited/synchronous.

Reproduction uses the candidate's harness with explicit source roots; no runner is
installed or built in the read-only reference. `campaign.mjs` takes `before|after|
concurrency` and `baseline|latest`, creates an append-only output directory and
validates the frozen inventory and exact runtime/image hashes. Use fresh output
locations for a new experiment. It refuses to overwrite existing campaign data.

```sh
python3 /tmp/mad-dom-bun-native-performance-efaa64b/activity.py --task 04 --kind sampling -- \
  /tmp/mad-dom-bun-performance-01/runtimes/baseline/bun-linux-x64/bun \
  scripts/bench-bun-io.mjs --checksum-worker \
  '{"sourceRoot":"/absolute/candidate/root","bunExecutable":"/absolute/bun","mode":"bun","warmup":2,"runs":9}'
```

The one-worker command is a building block; formal comparisons require both full
ABBA groups under one driver, as in `campaign.mjs`. Use `mode: "fallback"` for the
independent process gate. Internal module timing excludes startup; direct CLI
process timing includes startup and exit. The normal `bench:bun-io` rows use one
sample per side for smoke/report compatibility and are not formal ABBA evidence.
Checksum never loads the native image; its two overrides resolve to its source's
image, and the separate report:runtime/native tests prove actual native loading.
The experiment-only prototype links its ignored build path to this task's image.
To reproduce that experiment in another checkout, first build that checkout via
the required gate, then link `prototype/build/mad-dom.node` to its own image.
Do not copy or rebuild the frozen reference.

Preparation failures are retained:

1. `003-baseline-checksum-smoke` detected that Bun reuses file modules despite
   query-string changes. Its invocation count guard failed (exit 1); those times
   are invalid. The fixed worker evaluates a unique data module with the exact
   CLI source, only resolving relative imports/import.meta.url to the source.
   Direct process timings always execute the untouched actual CLI file.
2. `005-baseline-checksum-audit-smoke` returned a report but observed zero fs scans:
   Bun named built-in exports were not rebound by syncBuiltinESMExports. This
   preliminary diagnostic is not scan evidence. Audit-only data modules now bind
   the wrapped fs/crypto functions explicitly; formal workers install no hooks.
3. `009-baseline-host-tests` had 39 pass / 2 fail: a test tried assigning Bun's
   nonconfigurable global, and a test incorrectly required Node's EISDIR text on
   Bun's distinct directory-read error. `010` records the property descriptor;
   `011` passed after exercising the missing-global gate in an isolated realm and
   accepting the two existing diagnostic forms. No CLI error behavior changed.

The initial measured harness source is preserved in `before-harness-source.json`.
Later additions bind audit-only builtins and strengthen result guards outside
formal timed operations. The fixture construction, actual CLI evaluation loop,
startup window, samples and statistics protocol are unchanged. No historical
results were rewritten and no candidate source was modified during its campaign.

The concurrency prototype is retained only as reproducible evidence under
`prototype/`. It is not production code. Its stat-derived byte budget is for
immutable fixtures; it does not solve a file growing between stat/read. Production
remains one tarball at a time, with no batch scheduler or unawaited jobs.

Limits: warm filesystem/page cache from fixture creation and validation; unique
internal data-module parsing/JIT differs from direct CLI startup; endpoint/maxRSS
includes runtime/oracle allocations, so it is not a peak-live-buffer accounting
or leak proof. Separate host-call counts describe scheduled tarball bytes/files.
Shared VM load/CPU pressure/process snapshots cannot control other repositories.
Historical ~4× 1 MiB repeated-write figures are a separate microbenchmark and do
not identify manifest-write cost. The unchanged small-manifest strategy is not a
claim that Bun is always faster. Historical scratch/lifecycle/v2 RSS leak blind
spots remain; this task neither modifies nor improves those native protocols.
